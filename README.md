# vpnpa

## Что делает vpnpa

Локальные SOCKS5 (`127.0.0.1:1080`) и HTTP CONNECT (`127.0.0.1:8080`). Под ними клиент AmneziaWG 3.1 внутри процесса и уже слушающие чужие SOCKS5, в том числе AdGuard VPN CLI. Пользовательский трафик сидит на одном выбранном выходе, пока тот жив. Маршрут хоста не меняется, root не нужен.

## Сборка из исходников

Нужен Go 1.27.1.

```bash
go build -o vpnpa ./cmd/vpnpa
```

Обычный путь — скачать статический бинарник релиза в `~/.local/bin`, а не собирать самому. Релиз собирается на тег git: linux/amd64 и linux/arm64, `CGO_ENABLED=0`.

## Пример config.yaml

Файл лежит в `~/.config/vpnpa/config.yaml`. Права `0600`: в `vpn://` есть приватный ключ, в `socks5://` может быть пароль. `vpnpa add` и `vpnpa add-socks5` эти права не ослабляют.

```yaml
listen: 127.0.0.1:1080
http_listen: 127.0.0.1:8080
balancer:
  type: sticky
  check_interval: 15s
  check_timeout: 8s
  fail_threshold: 3
  recover_threshold: 2
  restart_interval: 5m
  check_urls:
    - https://www.gstatic.com/generate_204
    - https://cp.cloudflare.com/generate_204
backends:
  - id: vpn-1
    type: amneziawg
    priority: 100
    uri: vpn://ЗАГЛУШКА
  - id: adguard
    type: socks5
    priority: 90
    uri: socks5://127.0.0.1:1081
log:
  level: info
  format: text
```

`socks5://127.0.0.1:1081` — это пример AdGuard VPN CLI в режиме SOCKS, не отдельный тип бэкенда. Логин и `adguardvpn-cli connect -l` делает пользователь. vpnpa этот процесс не запускает и не останавливает. Свой слушатель vpnpa сюда указывать нельзя: получится петля.

`check_urls` заменяет список проб целиком. Запись `tcp://host:port` — дешёвая проверка, успех это открытый TCP.

## Первая установка

Без root, одной командой. Скрипт берётся из GitHub Release, рядом с бинарником:

```bash
curl -fsSL https://github.com/LDPet/vpnpa/releases/latest/download/install.sh | sh
```

Скрипт понимает только linux/amd64 и linux/arm64, сверяет sha256 и кладёт бинарник в `~/.local/bin/vpnpa`. Если этого каталога нет в `PATH`, строка `export` дописывается в `~/.bashrc` — откройте новый терминал. Дальше скрипт вызывает `vpnpa install`.

`vpnpa install` создаёт каталоги, пишет конфиг с пустым `backends` (только если файла ещё нет) и unit `~/.config/systemd/user/vpnpa.service`. Сервис не включается и не стартует: ссылок ещё нет. Повторный запуск конфиг со ссылками не затирает, unit обновляет. Если `systemctl --user` недоступен, команда печатает, что нужно войти в обычную сессию или выполнить `sudo loginctl enable-linger $USER`.

Дальше ссылку не надо вклеивать в YAML руками:

```bash
vpnpa add 'vpn://...'
vpnpa add-socks5 'socks5://127.0.0.1:1081'
vpnpa up
```

Первый бэкенд получает priority 100, следующий на 10 меньше. Имя `vpn-1`, `vpn-2`, если своё не передали флагом `--id`.

Повторный прогон `install.sh` обновляет бинарник так же, как `vpnpa update`: временный файл в том же каталоге и `rename`. Конфиг не трогает.

Пути без root:

- бинарник: `~/.local/bin/vpnpa`
- конфиг: `~/.config/vpnpa/config.yaml`
- unit: `~/.config/systemd/user/vpnpa.service`, `ExecStart` вызывает `vpnpa run`
- состояние: `~/.local/state/vpnpa/status.json`
- ключ API-ссылки: `~/.local/state/vpnpa/keys/<id>`, права `0600`

## Пользование

`vpnpa up` стартует user-сервис systemd, ждёт, пока SOCKS примет соединение, печатает адреса и выходит. Терминал не остаётся занятым. При пустом списке бэкендов команда выходит с ошибкой и текстом про `vpnpa add`, сервис не стартует.

`vpnpa down` останавливает сервис. `vpnpa status` читает файл состояния: слушатели, текущий бэкенд, кто жив, предпочтение, внешний IP. `vpnpa logs` показывает последние записи journal и сразу завершается. Следить дальше — `vpnpa logs -f`.

`vpnpa add` принимает только `vpn://`. `vpnpa add-socks5` принимает только `socks5://`. `vpnpa list` печатает id, тип и приоритет. Для SOCKS ещё host:port, без пароля и без самой ссылки.

`vpnpa prefer <id>` вручную выбирает выход, пока чините конкретную ссылку. Балансировщик сам приоритеты не перетасовывает: выздоровевший бэкенд с большим priority текущий не вытесняет. `vpnpa prefer auto` возвращает обычную липкость. Демон перечитывает предпочтение сам, перезапуск не нужен.

`vpnpa enable` поднимает сервис при входе в сессию. После выхода он живёт, только если включён linger: `sudo loginctl enable-linger $USER`. `vpnpa disable` снимает автозапуск.

`vpnpa update` качает latest-релиз, сверяет sha256, пишет бинарник во временный файл и делает `rename`. В запущенный файл напрямую писать нельзя: на Linux это `ETXTBSY`. Если сервис был запущен, команда его перезапускает.

`vpnpa run` — только отладка и то, чем unit запускает процесс. Он занимает терминал. Ctrl+C останавливает. В фон vpnpa сам не уходит.

Если сервис уже запущен, `vpnpa add` и `vpnpa add-socks5` шлют ему SIGHUP. Демон перечитывает конфиг. Запись с тем же id и тем же uri не переподнимается. Новый id поднимается, снятый гасится. Текущий выбор сохраняется, пока этот id ещё есть.

Флаги поверх файла: `--config`, `--state-dir`, `--log-level`, `--log-format`.

## Куда направить приложения

Основной адрес — HTTP CONNECT `127.0.0.1:8080`. Так Chrome и Cursor отдают домен, а DNS делает бэкенд внутри туннеля или на чужом SOCKS.

SOCKS5 `127.0.0.1:1080` — для программ, которые сами присылают имя. Имя уходит в `Dial` как есть, вход его не резолвит. Если клиент по SOCKS5 уже прислал IP, DNS он сделал сам, и этот запрос мог уйти мимо VPN. Для Chrome это обычное поведение SOCKS5, поэтому в инструкции основной адрес — HTTP CONNECT.

Пароля на входе нет. UDP ASSOCIATE нет. Слушатели только на loopback.

## Как читать лог

`log/slog` пишет в stderr. Под systemd stderr уходит в journal.

По info уже видно, кто текущий, когда бэкенд признали неживым и куда переключились. Строка `переключение` содержит id бэкендов и причину: `probe`, `prefer`, `start`. Секретов в логе нет: целиком `vpn://`, приватные ключи, `api_key`, preshared key и пароль SOCKS не пишутся.

`бэкенд жив` и `бэкенд нежив` — смена состояния после порога. Порог неудач по умолчанию 3 (`fail_threshold`), порог восстановления 2 (`recover_threshold`). Одна осечка порог не пересекает. `проба к порогу` на warn — неудача, которая двигает счётчик, но ещё не переключила выход.

Проба ходит по `check_urls` по порядку до первого HTTP 204. Ответил один из двух адресов — проба удачная. Не ответил ни один — неудачная. Раз в минуту отдельный запрос через текущий бэкенд узнаёт внешний IP. Ошибка этого запроса пробу не роняет и старый IP не стирает.

`нет живых бэкендов` и ошибка `no healthy backend` (`ErrNoHealthyBackend`) значат, что вход никуда не выпускает трафик. Своего выхода в интернет хоста нет. Уже открытые TCP после переключения не переносятся: они доживают на старом туннеле и рвутся вместе с ним.

Текущий бэкенд из-за пробы не закрывается. `Down` у него начинается после того, как выбор ушёл на другой, и не сразу, а по `restart_interval` (по умолчанию 5 минут). У бэкенда, который уже не текущий, на пороге один `Down`+`Up` и сразу ещё проба. Для `socks5` это пустой цикл: чужой процесс не рестартится.

Ошибка пользовательского dial текущий бэкенд не переключает. Она только просит внеочередную пробу. В warn есть `conn_id`, id бэкенда, адрес назначения и длительность.

Для разбора: `vpnpa run --log-level debug` или `log.level: debug`. На debug видны каждая проба, успешный dial и UAPI без ключей. Логгер `amneziawg-go` по умолчанию молчит; на debug видны handshake и ошибки устройства. Побайтный дамп пакетов не пишется.

Успешный трафик Chrome на info не пишется.

## Если не коннектится

1. Слушатель поднялся: `vpnpa status` или `ss` на `127.0.0.1:1080` и `127.0.0.1:8080`.
2. В логе бэкенд стал живым (`бэкенд жив`), а в status есть текущий id.
3. Ссылка именно `vpn://`, не файл `.conf` и не `socks5://` в `vpnpa add`.
4. Для API-ссылки с `api_endpoint` и `api_key` этот адрес доступен с хоста. Пара ключей лежит в `~/.local/state/vpnpa/keys/<id>` и переиспользуется, пока uri тот же. Смена uri у этого id — новый файл ключа. Запрос к API есть на `Up`, на dial его нет.
5. После поломки смотрите warn о переключении. Старый TCP сам на новый VPN не переедет: откройте соединение заново.
6. Если в конфиге `RandomTrailers=on` и `H1`–`H3` заданы диапазоном, бэкенд на `Up` пишет warn. Значения не переписываются: они должны совпадать с сервером. Часть пакетов при такой паре может теряться.
7. Зависший SOCKS AdGuard оживляет `adguardvpn-cli disconnect` и снова `connect`, не код vpnpa. Проба пометит выход мёртвым, пока порт не ответит.
